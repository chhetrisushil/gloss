# Gloss: v0 spec

16 Nov 2026 · @Sushil · revised 22 Nov 2026

Gloss v0 is a small, verb-led language that reads like plain sentences and compiles straight to a native executable, scoped to command-line programs over records and tables stored in files. Source files end in `.gloss`.

This revision closes the gaps found when the 16 Nov draft was reviewed. Appendix B lists every change and where it landed. Appendix B also lists everything this revision introduced without prior discussion; each of those needs a yes or a change.

---

## 1. Purpose and audience

The language exists to make program logic readable again, now that agents write most code and fewer people look at it.

- **Developers who have drifted from code** read and write it to stay close to algorithms and to what the machine does.
- **People who have never programmed** read what an agent wrote for them, check it through tests, and can change it themselves.
- **Agents** write it. The whole language must fit in a prompt, because no model has been trained on it. Appendix A is the complete grammar for that purpose.

## 2. Design rules

Every construct in the language must obey these six rules.

1. **Structured like code, worded like English.** Every statement starts with a fixed keyword, so nobody has to guess a phrasing.
2. **One form per idea.** There are no synonyms and no optional words. One idea never has two forms, and one form never means two ideas. Where a second form could mean the same thing, the compiler rejects it, its error names the accepted form, and `gloss format` rewrites it.
3. **No grammar words.** Articles, pronouns and plural handling are not part of the language. The short words that mark a role inside a fixed form (`to`, `of`, `with`, `in`, `from`, `by`, `into`, `as`) belong to that form; they are not free grammar.
4. **Symbols for arithmetic, words for everything else.** `+ - * /` compute; comparisons and logic are written in words.
5. **The compiler infers but never guesses.** Types and variables are worked out from the code, and anything inferred can be shown to the reader. A line that could be read two ways is a compile error that asks for parentheses, never a silent choice.
6. **Nothing hidden.** A program does only what its source says. Every line can show the machine instructions it became, or the named runtime routine it calls, and `gloss explain` prints that routine's instructions too. Code borrowed from outside Gloss is allowed only when it is named in the list shown at build time.

## 3. Program structure

A program is one source file made of four kinds of top-level block: `record`, `table`, `feature` and `test`.

- **Entry point:** the program begins at the feature named `start`. `start` has no `needs` line and gives nothing.
- **Blocks:** a block is the lines indented under its opening line. Indentation is exactly two spaces per level, and tabs are rejected.
- **Lines:** one statement per line. Blank lines are ignored. A long line may be broken after a comma; each continuation line is indented one level deeper than the line it continues. A statement never ends in a comma, so a continuation is never mistaken for a block.
- **Comments:** a line starting with `note` is ignored by the compiler. `note` alone on a line makes every line indented under it part of one comment. A comment cannot follow a statement on the same line. Tabs are not allowed in comments either.
- **Names:** letters, digits and underscores, starting with a letter, and case-sensitive. Record names start with a capital letter; every other name starts with a lowercase letter. Two names in the same program that differ only in case are a compile error. The one exception is a record name and a lowercase name that differ only in their first letter, such as `Expense` and `expense`, because the capital already tells them apart.
- **Who owns a name:**
  - Features, records and tables share one set of names across the program.
  - Variables belong to their feature or test, and cannot reuse a feature, record or table name.
  - Field names belong to their record and may repeat across records.
- **Reserved words.** Keywords can never be used as names:
  `add and append as ask at by clear divide each empty expect feature for from give greater if in input into is least less list load more most multiply needs no not note number of or otherwise places record repeat run save set show skip stop subtract table test text than to truth while with yes`
- **Built-in fact names** cannot be used as any name, field names included:
  `count first last item whole remainder shown`
  If they were allowed as field names, `count of x` would read a field or a built-in fact depending on the type of `x`. That is the same problem `append` fixed for `add`: a reader should not need a type to know what a line means. A CSV file with a column of one of these names needs the column renamed before a v0 program can load it.
- **Text:** written in double quotes, such as `"food"`. A double quote inside text is written twice: `"she said ""hi"""`. There are no other escapes, and text written in the source cannot hold a line break.

```gloss
note smallest complete program
feature start
  show "hello"
```

```gloss
note
  Walks the list once and keeps the largest value seen so far.
  An empty list is a run-time failure, because there is no first item.
feature largest
  needs numbers as list of number
  set biggest to first of numbers
  for each n in numbers
    if n is greater than biggest
      set biggest to n
  give biggest
```

## 4. Values and types

v0 has six types. The user declares a type in only three places: record fields, feature inputs and empty lists. Type names also appear in conversions (`cost as number`) and in the number check (`cost is number`).

| Type | Written as | Notes |
|---|---|---|
| number | `42`, `-7.5`, `120.50` | Fixed-point with four decimal places. See Numbers. |
| text | `"food"` | Cannot be changed once made. Compared with `is` and `is not` only. |
| truth | `yes`, `no` | The result of every comparison. |
| list of T | `list of 4, 9, 2` | T is number, text, truth or a record. Every item has the same type. Items are numbered from 1. Lists of lists are not in v0. |
| record | `Expense with name "Lunch", amount 120` | A fixed set of named fields, defined with `record`. Each field is a number, text or truth. |
| table | declared with `table` | A list of records of one type, bound to a file. |

An empty list needs its item type stated: `empty list of number`.

### Values and copies

Every value behaves as its own copy. Gloss does not have shared references, with one deliberate exception for loops.

- **`set` copies.** After `set b to a`, changing `b` never changes `a`, even when `a` is a list or a record.
- **The loop variable stands for the item, and cannot be replaced.**
  - Inside `for each expense in expenses`, changing a field of `expense` changes that row of the table: `set amount of expense to 0`.
  - Setting the loop variable itself is a compile error, whether with `set n to 0` or `add 1 to n`. That way the loop variable can never be used as scratch space by accident, which would overwrite items. The error names both ways out: "line 5: n stands for an item of numbers and cannot be set. To change the item, loop with for each i from 1 to count of numbers and set item i of numbers. To work on a copy, set m to n first."
  - In `for each i from 1 to 10`, `i` cannot be changed either.
- **A list cannot change while a loop walks it.** Inside `for each x in xs` you cannot `append` to `xs`, `set` it, `clear` it, `load` it or replace one of its items (`set item 1 of xs to 0`, `add 1 to item 1 of xs`). The same applies to any feature called from inside the loop that does these things to `xs`, at any depth. The compiler checks this, and the error names the call chain.
- **Feature inputs cannot be changed.** A feature that sets, adds to or appends to an input, or to a field or item of one, is a compile error. The error suggests working on a copy: `set mine to numbers`. Because inputs never change, passing a list to a feature costs nothing.
- **Tables are the only shared data.** A table is visible in every feature, and changes to it are seen everywhere.
- **Equality looks inside.** Two lists are equal when they have the same items in the same order, and two records are equal when every field is equal. Both sides of `is` must have the same type.

### Numbers

There is one kind of number. It behaves like a calculator that keeps four decimal places.

- **Fixed-point, not floating point.** `0.1 + 0.2` is exactly `0.3`, which money needs. Each result is rounded to four places, so the results are exact only to four places: `1 / 3` is `0.3333`, and `1 / 3 * 3` is `0.9999`.
- **Division keeps the fraction.** `7 / 2` is `3.5`.
- **Rounding.** Results with more than four places are rounded to four, with halves rounded away from zero. Multiplication and division work on a 128-bit intermediate, so nothing is lost before the rounding.
- **Range.** From −922,337,203,685,477.5808 to 922,337,203,685,477.5807, about 922 trillion in each direction. A result outside the range stops the program (failure 4). Nothing wraps around silently.
- **Literals.** A literal with more than four decimal places, or one outside the range, is a compile error.
- **`whole of`** drops the fraction toward zero: `whole of 3.5` is `3`, and `whole of -3.5` is `-3`.
- **`remainder of a by b`** is what is left after taking out as many whole `b`s as fit. Its sign follows `a`: `remainder of 7 by 2` is `1`, `remainder of -7 by 2` is `-1`, and `remainder of 7.5 by 2` is `1.5`. It is computed exactly, with no rounding. If `b` is 0 the program stops (failure 1).
- **Positions must be whole.** `item 2.5 of prices` stops the program with a plain message (failure 3).
- **Showing a number.** `show` drops trailing zeros, so `120.50` appears as `120.5` and `120.0` as `120`. To fix the number of places, write `total as text with 2 places`. That rounds for display and gives `120.50`. The count of places is a digit from 0 to 4, written in the source.

> **To consider later: floating point.** Science, statistics, graphics and data from other systems will eventually need it. When it is added, it should be a second, separately named type, so that inexact values are visible in the code. `number` stays fixed-point for good, and mixing the two should need an explicit conversion with `as`. It is not decided and not designed; it is recorded here so that the reasoning is not lost.

### Text

- Text is a sequence of UTF-8 bytes.
- `is` compares byte for byte, so case matters: `"Food" is "food"` is `no`.
- v0 cannot join, split, search or measure text. Section 14 covers this.

> **To consider later: putting text in order.** Text can only be compared with `is` and `is not`, so a v0 program cannot sort names, find the first name alphabetically, or binary-search a list of words. That is a surprising gap for a language about records and tables: sorting expenses by amount works, but sorting them by name does not. Numbers already have `is greater than` and `is less than`; text could get a matching pair worded for order rather than size:
>
> ```
> if name of a is before name of b
>   set first to a
> ```
>
> - `is before` and `is after` would compare two texts. Like every comparison, they would give `yes` or `no` and could not be chained.
> - The open question is what "before" means. Comparing Unicode code points is exact and never guesses (rule 5), but it puts `"Zoe"` before `"adam"` and `"é"` after `"z"`, which surprises non-programmers. Comparing without regard to case or accents reads naturally, but alphabetical order differs between languages, so it would need a fixed, documented rule.
> - Equal texts would be neither before nor after each other, so `is before` together with `is` covers every case.
>
> It would add no new type and no new statement, and it would unlock sorting, searching and grouping by text with the algorithms that already work for numbers. It is not decided and not designed; it is recorded here so that the reasoning is not lost.

### Truth

- A condition is any truth value, so a truth variable is used directly: `if done`, `if not done`.
- `done is yes` and `done is no` are rejected in favour of `done` and `not done`, following rule 2. `gloss format` rewrites them.

### Conversions

| Conversion | Result |
|---|---|
| `x as text`, x a number | The number as `show` prints it |
| `x as text with 2 places`, x a number | Rounded to exactly that many places: `120.50` |
| `x as text`, x a truth | `"yes"` or `"no"` |
| `x as number`, x a text | The number, or failure 5 if the text is not a number |

Text counts as a number only in this form:

- an optional `-`
- one or more digits
- optionally, a `.` followed by one to four digits

Spaces at either end are ignored. `"120.50"`, `" -7 "` and `"0.5"` are numbers. `"+3"`, `"1,200"`, `"1e3"`, `".5"` and `"0.12345"` are not. Use the check `x is number` to find out first.

Any other conversion is a compile error.

### Showing values

`show` prints its items one after another with nothing between them, then ends the line. Each item appears as follows:

| Value | Shown as |
|---|---|
| text | The text itself, with no quotes |
| number | As described under Numbers |
| truth | `yes` or `no` |
| record | Its Gloss source form: `Expense with name "Lunch", amount 120, category "food"` |
| list | Its Gloss source form: `list of 4, 9, 2`, or `empty list of number` |

## 5. Variables

A variable is created the first time it is set; there is no declaration keyword.

- **Creation.**
  - `set total to 0` creates `total` as a number.
  - `for each price in prices` creates `price` for the length of the loop.
  - `ask … into cost` creates `cost` as text, or replaces the value of an existing text variable.
- **Fixed type.** The type is inferred at the first `set` and never changes. Setting `total` to text later is a compile error. Sets in different branches of an `if` must agree on the type.
- **Lifetime.** A variable made by `set` or `ask` lives from its first set to the end of its feature or test. A loop variable lives only inside its loop. It cannot share a name with a variable already in scope, but two separate loops may each use the same name, with any type.
- **Features do not share variables.** Tables are the only shared data.
- **`is` never creates anything.** `if a is 10` only compares, so a reader always knows which lines change state.

The compiler makes these checks, because implicit variables fail quietly without them.

| Situation | Result | Message |
|---|---|---|
| A variable is read where it may not have a value yet. This includes reading, after a loop, a variable first set inside the loop, because the loop may run zero times. | Error | "line 9: a may not have a value here; it is first set inside the if on line 5. Set it before the if." |
| A name is read that is never set | Error | "line 9: totl has no value. Did you mean total?" |
| A variable is set but never read | Warning | "line 4: totl is set but never used" |
| A new name of four letters or more is one letter away from an existing one. Pairs that differ only by a final `s`, such as `price` and `prices`, are exempt. | Warning | "line 6: new name totl; did you mean total?" |

## 6. Expressions

An expression computes a value and never changes anything.

| Kind | Forms |
|---|---|
| Arithmetic | `a + b`, `a - b`, `a * b`, `a / b`, `-a`, with `( )` for grouping |
| Comparison | `is`, `is not`, `is greater than`, `is less than`, `is at least`, `is at most` |
| Number check | `cost is number`, `cost is not number` (text only) |
| Logic | `and`, `or`, `not` |
| Field of a record | `amount of expense` |
| Built-in facts | `count of prices`, `first of prices`, `last of prices`, `item 2 of prices`, `remainder of 7 by 2`, `whole of 3.5` |
| Feature call | `category_total with "food"`, or `largest_expense` alone for a feature with no inputs |
| Building | `Expense with name "Lunch", amount 120, category "food"`, `list of 4, 9, 2`, `empty list of number` |
| Conversion | `cost as number`, `total as text`, `total as text with 2 places` |

- **`of` reads, `with` calls or builds.**
  - `X of Y` reads a field or built-in fact from `Y`.
  - `F with A, B` runs feature `F` with those inputs.
  - `Record with field value, …` builds a record. A capital letter tells a record apart from a feature.
- **Precedence**, from tightest to loosest:
  1. Plain values: numbers, text, `yes`, `no`, names, `empty list of T`, and anything in parentheses
  2. Facts with `of`, read right to left: `name of item 2 of students` is the name of the second student
  3. Negation: `-x`
  4. Conversion: `as number`, `as text`, `as text with N places`
  5. `*` and `/`
  6. `+` and `-`
  7. Open forms: a feature call with inputs, record building, list building
  8. Comparisons and the number check
  9. `not`
  10. `and`, `or`
- **Facts bind tightest.** `count of prices + 1` is `(count of prices) + 1`, and `amount of expense * 2` is `(amount of expense) * 2`; no other reading would type-check.
- **A number fact never sits bare before arithmetic.** `whole of` and `remainder of … by …` work on numbers, so `whole of a / b` could mean `(whole of a) / b` or `whole of (a / b)`. Following rule 5, a `whole` or `remainder` fact directly followed by `+ - * /` is a compile error asking for parentheses: "line 8: whole of a / b can be read two ways. Write (whole of a) / b or whole of (a / b)."
- **Positions are simple.** The position in `item` is a number, a name or something in parentheses: `item (i + 1) of prices`.
- **Open forms reach to the end of their list.** Feature inputs, field values and list items are arithmetic. A comparison is passed as an input in parentheses: `check with (x is 3)`. An open form used as an operand of `+ - * /`, `as` or `of` must be in parentheses: `1 + (category_total with "food")`. An open form can stand on either side of a comparison without parentheses: `expect category_total with "food" is 420`.
- **Open forms inside comma lists are always in parentheses.** These are comma lists: `show` items, list items, feature inputs and record fields. Inside one of them, a feature call with inputs, a record being built or a list being built is always in parentheses, even with a single input. Examples: `show "Total: ", (category_total with kind)` and `list of (Student with name "Asha", marks 82), (Student with name "Ravi", marks 67)`. There are no exceptions, so a reader never has to work out which list a comma belongs to.
- **Comparisons do not chain.** `a is b is c` is a compile error.
- **`and` and `or` do not mix without parentheses.** `a and b or c` is a compile error. Write `(a and b) or c` or `a and (b or c)`.
- **No built-in shortcuts for logic.** There is no `sum of` or `sort`; writing those is the point of the language.

## 7. Statements

v0 has 24 statement forms, and each idea has exactly one.

| Statement | Meaning |
|---|---|
| `note any words` | Comment; ignored. Alone on a line, it makes the indented lines under it one comment. |
| `set total to 0` | Give a variable, field or list item a value |
| `add price to total` | `total` becomes `total + price` (numbers only) |
| `subtract discount from total` | `total` becomes `total − discount` |
| `multiply total by 2` | `total` becomes `total × 2` |
| `divide total by people` | `total` becomes `total ÷ people` |
| `append lunch to expenses` | Put an item at the end of a list or table |
| `show "Total: ", total` | Print the items on one line |
| `ask "How much?" into cost` | Print the question on its own line and read one line into a text variable |
| `if price is greater than 100` | Run the block when the condition holds |
| `otherwise if price is less than 80` | Next branch; the first matching branch wins |
| `otherwise` | Final branch |
| `for each price in prices` | Run the block once per item |
| `for each i from 1 to 10` | Run the block once per number, counting up, both ends included |
| `repeat while total is less than 100` | Run the block while the condition holds |
| `skip` | Go to the next turn of the innermost loop |
| `stop` | Leave the innermost loop |
| `give total` | End the feature and hand back a value |
| `run print_report with expenses` | Call a feature that gives nothing |
| `load expenses` | Read a table from its file |
| `save expenses` | Write a table to its file |
| `clear expenses` | Empty a table on purpose, so that it can be saved without being loaded |
| `expect total is 420` | In a test: fail unless the condition holds |
| `input "Lunch", "120"` | In a test: the answers the next `ask`s receive, in order |

- **Verbs update, symbols compute.** A `set` whose right side is just the target combined with one other value is a compile error, and `gloss format` rewrites it:

  | Written | Accepted form |
  |---|---|
  | `set t to t + x` or `set t to x + t` | `add x to t` |
  | `set t to t - x` | `subtract x from t` |
  | `set t to t * x` or `set t to x * t` | `multiply t by x` |
  | `set t to t / x` | `divide t by x` |

  The rule applies only when the target itself is one side of the outermost operation. `set t to x - t` and `set t to t * 2 + 1` are accepted as written.
- **`add`, `subtract`, `multiply` and `divide` work on numbers only.** The target is a variable, a field or a list item holding a number: `add 30 to amount of lunch`, `add 1 to item 3 of scores`.
- **`append` works on lists and tables only.** `append 5 to scores` puts 5 at the end. `add 5 to scores` is a compile error that suggests `append`.
- **`for each … from … to`.** Both ends are worked out once, before the first turn, and must be whole numbers (failure 3). If the start is greater than the end, the block runs zero times. To count down, count up and compute: `set n to top - i + 1`.
- **`skip` and `stop`** act on the innermost loop. Outside a loop they are a compile error.
- **`give`** ends the feature. The rules for `give` are in section 9.
- **`run`** is for features that give nothing. Using `run` on a feature that gives a value is a compile error: "category_total gives a number; use it, as in set result to category_total with "food"". Using a feature that gives nothing inside an expression is also a compile error.
- **`ask`.** The question is any text value. The line read has its ending (`\n` or `\r\n`) removed. A last line with no ending still counts as a line. If input has ended with nothing read, the program stops (failure 9).
- **`expect` and `input`** are allowed only in tests. Everything else is allowed in tests too; section 9 explains how tests handle files and input.

> **To consider later: choosing by value.** v0 has no `switch` or `case`. A long choice is written as an `if` chain, and `otherwise if` keeps it flat:
>
> ```
> if category of expense is "food"
>   add amount of expense to food_total
> otherwise if category of expense is "travel"
>   add amount of expense to travel_total
> otherwise
>   add amount of expense to other_total
> ```
>
> What hurts is repeating `category of expense is`, not how deep the code goes. That costs typing and adds noise, but any reader can follow it without learning anything new. Where non-programmers struggle with `switch` in other languages, it is usually the words and the quirks, not the idea: `switch` and `case` mean nothing to them, and a forgotten `break` makes one branch fall into the next. "Depending on this value, do one of these" is familiar to anyone who has read a menu or a form.
>
> If it is added, it should read as a sentence and have no quirks:
>
> ```
> depending on category of expense
>   when "food"
>     add amount of expense to food_total
>   when "travel"
>     add amount of expense to travel_total
>   otherwise
>     add amount of expense to other_total
> ```
>
> - Exactly one branch runs. There is no fall-through and no `break`.
> - It only tests equality. Ranges and other conditions stay with `if`.
> - `otherwise` is reused, so the ending is already known.
> - The words `depending on` and `when` are a sketch, not a decision.
>
> The cost is rule 2: the same idea would have two forms. Keeping the rule means the compiler must draw a boundary. For example, an `if` chain of three or more branches that all compare the same value would be rejected, and `gloss format` would rewrite it, the way `set` and `add` are handled. That works, but it is one more rule to explain.
>
> It waits for three reasons. There is no evidence yet that it is needed: v0 programs are small, and a four-branch chain reads fine. The spec has just grown a lot, with many new items still awaiting approval. And adding it later breaks nothing, because existing chains stay valid until the formatter rewrites them. It is not decided and not designed; it is recorded here so that the reasoning is not lost.

## 8. Records and tables

A record is one thing with named fields; a table is a list of records of one type that is kept in a file.

```gloss
record Expense
  name as text
  amount as number
  category as text

table expenses of Expense in "expenses.csv"
```

- **Create a record:** `set lunch to Expense with name "Lunch", amount 120, category "food"`. Every field must be given, once.
- **Read a field:** `amount of lunch`.
- **Change a field:** `set amount of lunch to 150`, or `add 30 to amount of lunch`.
- **Change a row of a table** through the loop variable, or by position:

  ```gloss
  for each expense in expenses
    if category of expense is "food"
      multiply amount of expense by 2
  set amount of item 3 of expenses to 150
  ```
- **Tables are shared.** A table is declared at the top level and is visible in every feature.
- **Tables behave like lists.** `append lunch to expenses`, `for each expense in expenses`, `count of expenses` and `item 2 of expenses` all work. A table can be given to a feature input of type `list of Expense`; the feature sees it read-only, like any input.
- **One file, one table.** Two table lines that name the same file are a compile error.
- **Files are explicit.** `load expenses` reads the file and `save expenses` writes it. Nothing is read or written unless a line says so. A `load` replaces whatever rows the table already holds. If rows appended earlier in the same feature would be replaced, the compiler warns.
- **A missing file loads as an empty table** and prints a one-line notice, such as "expenses.csv not found; starting with an empty table". The notice goes to the error output, so it never mixes with what the program shows.

### File format

Tables are stored as CSV, following RFC 4180.

- **Encoding and layout.** UTF-8 text, with commas between cells. The first row is a header.
- **Header.**
  - It names every field of the record exactly once, in any order. Rows are matched to fields by name.
  - A missing, extra, repeated or misspelled column stops the program (failure 6). The message names the column.
- **Quoting.** A cell containing a comma, a double quote or a line break is wrapped in double quotes, and the quotes inside it are doubled.
- **Cells.** A text cell is taken as it is, and may be empty.
  - A number cell must pass the number check from section 4. An empty number cell is failure 6.
  - A truth cell is `yes` or `no`.
- **Line endings.** Reading accepts `\n` and `\r\n` line endings and ignores one final empty line.
- **Writing.** `save` writes:
  - the header in the order the fields are declared
  - numbers as `show` prints them
  - truths as `yes` and `no`
  - quotes only where needed
  - `\n` line endings
- **Bad data.** A failure caused by the file names the file and its line, as in "expenses.csv line 7: amount "12,50" is not a number".

### Saving

`save` is the mirror of `load`: after a load the table matches the file, and after a save the file matches the table.

| Situation | What `save` does |
|---|---|
| The table was not loaded or cleared earlier in this run | Stops the program (failure 8); the file is untouched |
| The file does not exist | Creates it, with the header row and every row in the table |
| The file exists | Replaces its whole content with the table's current rows |
| The folder does not exist, or the file cannot be written | Stops the program (failure 7) |

- **A table must be loaded or cleared before it is saved.** Saving replaces the file, so a forgotten load would wipe every earlier row. Two checks guard against this:
  - **At build time:** a program that saves a table but never loads or clears it anywhere is a compile error. The error names the fix: "line 12: expenses is saved here but nothing in this program loads it. Add load expenses before the first change, or clear expenses if you mean to start the file again."
  - **At run time:** each table remembers whether it has been loaded or cleared in this run. Saving one that has not is failure 8, before anything is written. This check follows the program's real path, so `start` can load a table and a helper feature can save it.
- **`clear` states the intent.** `clear expenses` empties the table, and is how a program says it means to rebuild the file from scratch. `clear` applies to tables only; a list is emptied with `set xs to empty list of T`.
- **No append-to-file verb.** Adding rows to a file is written as `load`, `append`, `save`. Writing single rows straight to a file is left for after v0.
- **Safe writing.** `save` writes `expenses.csv.gloss-new` in the same folder, flushes it to disk, and then renames it over `expenses.csv`. A crash part-way leaves the old file intact. A leftover `.gloss-new` file from an earlier crash is overwritten.

### File permissions

A program can touch only the files named in its table lines, and the build must be told to allow each one. No Gloss statement opens any other file, uses the network or runs another program.

- **File names are fixed.** The name in a table line is written out in the source, never computed.
- **File names are relative.**
  - Folders are separated with `/`. A name may go into subfolders, as in `"data/expenses.csv"`.
  - Absolute paths, `..`, and empty parts such as `a//b` are compile errors.
- **File names are plain.** A file name may not contain control characters or invisible formatting characters, so the permission list always shows exactly the file the program opens.
- **One ending is reserved.** A file name may not end in `.gloss-new`, which Gloss uses for the temporary file while saving.
- **Names that read as options are refused.** A file name may not start with `-`, which a command line would take for an option.
- **Spaces must show.** No part of a file name may start or end with a space, because the permission list could not show it clearly.
- **Quotes are refused.** A file name may not contain `"`, because the permission list writes some names in quotes.
- **More endings are reserved.** A file name may not end in `.gloss`, `.allow`, `.trace` or `.svg`, which are kept for files Gloss reads or writes.
- **Case-only differences are warned about.** Two table files whose names differ only in case get a warning, because on some systems they are the same file.
- **Files are found from the current folder,** which is the folder the program is run from. `expenses.csv` means the file of that name there. The person running the program chooses where its data lives by choosing where to run it.
- **Symbolic links are refused.** At run time, a table path that passes through a symbolic link at any point stops the program: failure 6 on load, failure 7 on save. Without this, a link could point a table at any file on the machine. Files are opened with Linux's `openat2` and the flags `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`.
- **Every build shows the list.** A table that is never saved is listed as read only. Saving also writes the temporary `.gloss-new` file beside the table; that is part of "replace".

```
This program can:
  read and replace   expenses.csv
  read only          rates.csv
  nothing else
```

- **Approval.** Run by hand, the compiler shows the list and asks yes or no. Run by an agent or a script, each file must be named with `--allow expenses.csv`. That approves whatever access the source needs for that file.
- **What approval guarantees.** When a person answers the question, a person has approved. When an agent builds, the agent can pass `--allow` or edit the `.allow` file itself. In that case approval guarantees only that file access is declared and visible, not that a person agreed.
  - The control for agent builds is review. Every change to file access shows up in the source's table lines and in the `.allow` file, and the executable prints its list with `--permissions`.
  - Requiring a person for agent builds, for example by protecting the `.allow` file in code review, is left to the setup around Gloss.
- **Approvals are kept in a plain file** beside the source: `expenses.gloss` has `expenses.allow`. It lists each approved file and its access, in the same form as the list above, under a `note` line saying what it is. Commit it with the source.
  - A build whose list is covered by the approvals asks nothing, but still prints the list.
- **New access needs new approval.** These need a fresh approval before the build succeeds:
  - a file that has not been approved
  - a file that moves from read only to read and replace

  A refused approval writes no executable (exit status 4).
- **The executable carries its list.** Running it with `--permissions` prints the list and does nothing else.

Approval happens at build time and not at run time, because the list is complete before the program runs. This guards against a Gloss program doing more than its source says. It does not make an executable built with some other tool safe; only the operating system guards against that.

### Lists of records

A list of records lives inside one feature and needs no table or file. This program prints "Top student: Meera with 91" and then "Second in list: Ravi".

```gloss
record Student
  name as text
  marks as number

feature start
  set asha to Student with name "Asha", marks 82
  set ravi to Student with name "Ravi", marks 67
  set meera to Student with name "Meera", marks 91
  set students to list of asha, ravi, meera

  set top to first of students
  for each student in students
    if marks of student is greater than marks of top
      set top to student

  show "Top student: ", name of top, " with ", marks of top
  show "Second in list: ", name of item 2 of students
```

- **Start empty and grow:** `set students to empty list of Student`, then `append Student with name "Asha", marks 82 to students`.
- **Records inside a list need parentheses**, under the comma rule in section 6: `list of (Student with name "Asha", marks 82), (Student with name "Ravi", marks 67)`. Without them it is a compile error.
- `set top to student` copies the record, so changing `top` afterwards would not change the list.

## 9. Features and tests

A feature is a named piece of logic; a test is a named check that the logic does what its title says.

```gloss
feature category_total
  needs wanted as text
  set total to 0
  for each expense in expenses
    if category of expense is wanted
      add amount of expense to total
  give total

test "category total is zero when nothing matches"
  expect category_total with "rent" is 0
```

### Features

- **Inputs.** An optional first line, `needs a as number, b as text`, names each input and its type. Inputs cannot be changed (section 4).
- **Result.**
  - `give` ends the feature and hands back a value. The result type is inferred, and every `give` in one feature must agree.
  - A feature that gives a value must give on every path. "line 14: category_total can reach its end without giving a value" is a compile error.
  - A feature with no `give` gives nothing.
- **Calling.**
  - Inside an expression: `category_total with "food"`.
  - On its own, by name, when it has no inputs: `largest_expense`.
  - As a statement for a feature that gives nothing: `run print_report with expenses`.
- **Recursion.** A feature may call itself, directly or through other features. Its result type is taken from the first `give`, in source order, whose type can be worked out without calling back into the same cycle. If every `give` depends on the cycle, the compiler asks for a base case: "line 3: cannot work out what countdown gives; add a give that does not call countdown".
- **Depth.** Every call checks the room left on the stack. Calls nested too deep stop the program with failure 10 instead of crashing.

Calling one feature from another. In this program `start` calls `report`, which calls `count_even`, which calls `is_even`. It prints "Even numbers: 2".

```gloss
feature is_even
  needs n as number
  give remainder of n by 2 is 0

feature count_even
  needs numbers as list of number
  set found to 0
  for each n in numbers
    if is_even with n
      add 1 to found
  give found

feature report
  needs numbers as list of number
  show "Even numbers: ", (count_even with numbers)

feature start
  set numbers to list of 4, 9, 2, 7
  run report with numbers
```

`is_even with n` and `count_even with numbers` are calls used for their value. `run report with numbers` is a call used for its effect, because `report` gives nothing back.

### Tests

- **Title.** A sentence in quotes, written so that a non-programmer can judge whether it is the right promise. Titles are unique within a program.
- **Checks.** `expect` followed by any condition. A test passes when every `expect` holds and no run-time failure happens.
- **Tables start empty.** Every table starts empty in each test, and counts as cleared, so it can be saved straight away.
- **Files are pretend.** In a test, `load` and `save` work exactly as in a real run. The difference is that each table's file is a pretend file that lives in memory. It starts missing, and it is thrown away when the test ends. No real file is ever touched, so tests need no approval.
- **`ask` gets its answers from `input`.**
  - `input "Lunch", "120"` queues answers. Each `ask` takes the next one.
  - An `ask` with no answer left fails the test: "the test gave 2 answers but line 31 asked a third question".
- **`shown` holds what the program printed.** In a test, `shown` is a list of text holding every line printed by `show` so far, in order. Questions from `ask` and notices on the error output are not included. Check it with the usual facts: `expect last of shown is "Total for food: 420"`.
- **Output is quiet.** Lines printed during a test appear only if the test fails, under its title.
- **How fixtures are built.** Pretend files, `input` and `shown` are a second backend for the runtime's file and console routines, chosen in test builds. The CSV reading and writing code is the same code a real run uses; only where the bytes come from and go to changes. They are built after plain tests work (section 12, step 3). If v0 runs late, they can move to v0.1 without changing anything else in the language.
- **Running.** `gloss test` builds an executable that runs every test and prints each title with pass or fail. For a failure it also prints the line of the first failed `expect` or the run-time failure. `start` does not run by itself in test mode; a test calls it with `run start` when it wants to.

A test can now check a whole program, including its questions and files:

```gloss
test "a new expense is saved and counted in its category"
  append Expense with name "Lunch", amount 120, category "food" to expenses
  save expenses
  input "Dinner", "300", "food"
  run start
  expect count of expenses is 2
  expect first of shown is "Total for food: 420"
```

## 10. Compiler behaviour

The compiler has six modes, and its messages are part of the language design.

| Mode | What it does |
|---|---|
| Build | Checks the program, asks for approval of its file access, and writes an executable |
| Test | Builds and runs every test block |
| Format | Rewrites the file into the one accepted form |
| Trace | Runs the program and narrates each step in plain words |
| Explain | Prints each source line beside the machine instructions it became |
| Flowchart | Draws each feature as a flowchart and writes it as an image file, without running the program |

### Errors

Error messages always give:

- the line number
- the line itself
- the problem in plain words
- the nearest valid form

For example: "line 7: set total as 0. set needs to. Did you mean set total to 0?"

### Format

`gloss format` makes these changes:

- Normalises spacing: one space between words, one space around `+ - * /`, and no space before a comma.
- Removes trailing spaces.
- Puts exactly one blank line between top-level blocks and keeps at most one blank line inside a block.
- Breaks lines longer than 100 characters after a comma, using the continuation rule.
- Applies the rewrites named in this spec:
  - the arithmetic `set` forms (section 7)
  - `is yes` and `is no` (section 4)

It never changes what a program does. Other compile errors, including tabs, are reported, not fixed.

### Run-time failures

Run-time failures stop the program with a plain message, the failure's number and the line, as in "line 12: failure 1: dividing by zero (people is 0)". v0 has ten:

| # | Failure | Message |
|---|---|---|
| 1 | Dividing by zero, with `/`, `divide` or `remainder` | `line 5: failure 1: dividing by zero (people is 0)` |
| 2 | Asking for an item that is not in the list: a position below 1 or above the count, or `first` or `last` of an empty list | `line 5: failure 2: there is no item 7 in prices; it has 3 items`, or `…: there is no first item in prices; it is empty` |
| 3 | A number that must be whole is not: an `item` position or a `for each … from … to` start or end (the start is checked first) | `line 5: failure 3: an item position must be whole (n is 2.5)`, `…: the end of a count must be whole (top is 2.5)`, or `…: the start of a count must be whole (low is 0.5)` |
| 4 | A number result is outside the range | `line 5: failure 4: a number went out of range (price * 1000000)` |
| 5 | Converting text that is not a number | `line 5: failure 5: "12a" is not a number (answer as number)` |
| 6 | A table file that exists but cannot be read, does not match its record, or is reached through a symbolic link | Worded in milestone 3 |
| 7 | A table file that cannot be written, or is reached through a symbolic link | Worded in milestone 3 |
| 8 | Saving a table that was not loaded or cleared earlier in this run | Worded in milestone 3 |
| 9 | Input ended while `ask` was waiting | `line 5: failure 9: input ended while ask was waiting` |
| 10 | Out of memory, or calls nested too deep | `line 5: failure 10: out of memory`, or `…: calls nested too deep (countdown)` |

- The message goes to the error output, and the program exits with status 2. Anything already shown is printed first.
- The words in parentheses come from the source line: the value or expression that failed, or, for failure 10, the feature being called. They are written as `gloss format` writes them, so `a*b` appears as `a * b`.
- Failure 5 shows at most 40 characters of the text, ending with `…` when cut, writes invisible characters as `\u{XXXX}`, and doubles a `"` inside the text, as in a text written in the source.

### Trace

Trace is for readers who want to follow the logic:

```
line 4: price is 150
line 5: 150 is greater than 100, so the block runs
line 6: total becomes 150
```

The narration goes to the standard output, together with the program's own lines, in the order they happen. That way questions, answers and shown lines appear where they belong in the story.

**Trace events.** A trace build adds a hook after every statement that writes one event per line to a file. The sentences above are printed from these events, and the step-through viewer in section 15 replays the same file.

Values in events are written as a JSON object with one key naming the type:

- a number: `{"number":"120.5"}`, written as a string so that no viewer turns it into floating point
- text: `{"text":"food"}`
- a truth: `{"truth":"yes"}`
- a list: `{"list":[…]}`
- a record: `{"record":"Expense","fields":{…}}`

```json
{"line":4,"event":"loop","name":"price","turn":2,"value":{"number":"150"}}
{"line":5,"event":"check","condition":"price is greater than 100","values":{"price":{"number":"150"}},"result":"yes"}
{"line":6,"event":"set","name":"total","from":{"number":"0"},"to":{"number":"150"}}
```

| Event | Written when | Carries |
|---|---|---|
| set | A variable, field or list item changes | Name, old value, new value |
| check | A condition is evaluated | The condition, the values in it, the result |
| loop | A loop starts a new turn | Loop variable, turn number, value |
| enter | A feature is called | Feature name, inputs |
| leave | A feature gives its result, or ends | Feature name, result if any |
| show | A line is printed | The text |
| ask | A line is read | The question, the answer |
| file | A table is loaded, saved or cleared | Table name, file name, what happened, row count |
| fail | The program stops on a run-time failure | Failure number, message |

Every event also carries its source line number.

### Explain

Explain is for readers who want to see the machine:

```
add price to total
    mov rax, [rbp-16]       ; price
    add [rbp-8], rax        ; total
    jo  fail_number_range   ; failure 4 if the result is out of range
```

- Explain lists what was inferred, such as "total: number, created on line 2".
- After the program's lines, Explain prints each runtime routine the program uses, such as `multiply_number`, `show_number` and `load_table`, with its own instructions. Nothing the executable runs is left out.

## 11. Building and running

One command, `gloss`, does everything; a build produces a single executable that runs on its own.

### Build, then run

```
$ gloss build expenses.gloss
This program can:
  read and replace   expenses.csv
  nothing else
Allow? yes
Approval saved in expenses.allow
Built expenses

$ ./expenses
What did you buy?
```

- The executable is named after the source file and is written beside it: `expenses.gloss` becomes `expenses`.
- It needs nothing else to run. Gloss does not have to be installed on the machine that runs it, as long as that machine is the same kind as the build target.
- Files are found from where it is run. `expenses.csv` means the file of that name in the current folder.

### All commands

| Command | What it does |
|---|---|
| `gloss build expenses.gloss` | Checks the program, asks for approval of its files, writes the executable `expenses` |
| `gloss test expenses.gloss` | Runs every test block and prints each title with pass or fail |
| `gloss format expenses.gloss` | Rewrites the file into the one accepted form |
| `gloss trace expenses.gloss` | Runs the program, prints each step in plain words, and writes the events to `expenses.trace` |
| `gloss explain expenses.gloss` | Prints each source line beside its machine instructions, then the runtime routines it uses |
| `gloss flowchart expenses.gloss` | Writes one SVG file per feature beside the source, such as `expenses.category_total.svg` |
| `./expenses --permissions` | Prints the files the executable can touch, and does nothing else |

The files that `gloss` itself writes are tools' output, not the program's file access. That covers the executable, `.allow`, `.trace` and `.svg` files, and none of them appears in the permission list.

### Options and results

- `--allow expenses.csv` on `build` or `trace` approves a file without the yes or no question, and records it in the `.allow` file. It is repeated once per file. `test` never asks, because tests use pretend files.
- A failed check writes no executable. Errors are printed with their line numbers. Warnings are printed and the build continues.
- **Exit status** tells agents and scripts the outcome without reading the output:

| Status | Meaning |
|---|---|
| 0 | Success; for `gloss test`, every test passed |
| 1 | `gloss test`: at least one test failed |
| 2 | A run-time failure, from the executable or from `gloss trace` |
| 3 | A compile error |
| 4 | File access was not approved |

## 12. Compilation target and runtime

The compiler writes a finished executable itself, with no outside assembler, linker, C library or LLVM in between. That is how v0 is built, not a permanent rule: design rule 6 allows borrowed code later, provided it is declared.

**Target.** The single v0 target is x86-64 Linux, kernel 5.6 or later, because `openat2` is needed for the symbolic-link rule. macOS is not a v0 target: it does not support static executables that make system calls directly. Apple Silicon also needs signed executables and goes through `libSystem`, which rule 6 would require to be declared as borrowed code.

The compiler writes the bytes itself, so it can run on any machine, macOS included, and still produce Linux executables. Running the result needs Linux, and so do `gloss test` and `gloss trace`. On a Mac that means a Linux container or virtual machine.

### Pipeline

1. Split the source into words, symbols and indentation levels, and join continuation lines.
2. Parse the lines into a tree of blocks and statements, following Appendix A.
3. Check names, infer types, and run the variable checks (section 5). Then run the loop checks and input checks (section 4), and the save check (section 8).
4. Generate machine code for each statement, with no optimisation.
5. Write the executable file (static ELF) with the runtime included.

Code generation is deliberately naive so that Explain stays readable: every variable lives in an 8-byte stack slot, and every expression leaves its result in one register.

### Runtime

The runtime is written in a small assembly language built into the compiler, so that Explain can print it. It reaches the operating system only through direct system calls. Every routine has a name, and Explain uses those names.

| Part | v0 behaviour |
|---|---|
| Value | Every value fits in 8 bytes, in one register or stack slot. Numbers and truths are held directly. Text, lists and records are held as the address of a block. |
| Number | 64-bit signed count of ten-thousandths, so `120.50` is stored as `1205000`. Adding and subtracting check for overflow. Multiplying and dividing use a 128-bit intermediate and round half away from zero. |
| Truth | 1 for `yes`, 0 for `no` |
| Text | A block holding the length, then the UTF-8 bytes; never changed in place |
| List | A header block holding the length, the capacity and the address of the items, 8 bytes per item. Growing copies the items to a block twice the size. The header stays put, so a loop variable keeps pointing at the right item. |
| Record | A block of 8 bytes per field, in declaration order |
| Copies | A list or record is copied, with the records inside a list, whenever it is stored: by `set` (including `set item`), by `append`, and as an item of `list of`. A value built by the stored expression itself (`list of`, `empty list of`, `E with`) is not copied again. A feature's result is copied too, because it may be one of the caller's own values passed in. Inputs are passed without copying, because they cannot change. Text is never copied, because it never changes. |
| Memory | One growing region taken with `mmap`. Nothing is freed before the program ends. Failing to grow is failure 10. |
| Stack | Each feature call compares the stack pointer with a limit worked out at start, and stops with failure 10 before the stack runs out |
| Console | Print text and numbers to standard output, notices to the error output; read one line from standard input |
| Files | Read and write a whole CSV file for `load` and `save`, with the safe-writing and symbolic-link rules from section 8 |

### Build order (proposed)

1. Lexer, parser, checker, error messages, and Format.
   Every example in this spec becomes a test of the compiler, with fixed expected output.
2. The native code generator, the ELF writer and the runtime. Build, plain tests and Trace work at this point.
3. Test fixtures: pretend files, `input` and `shown` (section 9).
4. Explain.
5. Flowchart.

There is one execution engine, the native one. The examples' fixed expected output, not a second engine, is what checks it.

## 13. Complete example

This expense tracker uses every top-level block and most statements. It records one expense, saves it, and reports on that category. If the cost typed is not a number, it asks again instead of stopping.

```gloss
note Expense tracker: record one expense, then report on its category

record Expense
  name as text
  amount as number
  category as text

table expenses of Expense in "expenses.csv"

feature category_total
  needs wanted as text
  set total to 0
  for each expense in expenses
    if category of expense is wanted
      add amount of expense to total
  give total

feature largest_expense
  set largest to first of expenses
  for each expense in expenses
    if amount of expense is greater than amount of largest
      set largest to expense
  give largest

feature ask_amount
  ask "How much did it cost?" into cost
  repeat while cost is not number
    ask "Please type a number, such as 120.50" into cost
  give cost as number

feature start
  load expenses
  ask "What did you buy?" into bought
  set cost to ask_amount
  ask "Which category?" into kind
  append Expense with name bought, amount cost, category kind to expenses
  save expenses
  show "Total for ", kind, ": ", (category_total with kind)
  set biggest to largest_expense
  show "Largest so far: ", name of biggest, " at ", amount of biggest

test "category total counts only the matching category"
  append Expense with name "Lunch", amount 120, category "food" to expenses
  append Expense with name "Bus", amount 40, category "travel" to expenses
  append Expense with name "Dinner", amount 300, category "food" to expenses
  expect category_total with "food" is 420
  expect category_total with "rent" is 0

test "largest expense is found"
  append Expense with name "Bus", amount 40, category "travel" to expenses
  append Expense with name "Dinner", amount 300, category "food" to expenses
  expect name of largest_expense is "Dinner"

test "a cost that is not a number is asked for again"
  input "Dinner", "abc", "300", "food"
  run start
  expect amount of first of expenses is 300

test "a new expense is added to the saved ones and reported"
  append Expense with name "Lunch", amount 120, category "food" to expenses
  save expenses
  input "Dinner", "300", "food"
  run start
  expect count of expenses is 2
  expect item 1 of shown is "Total for food: 420"
  expect item 2 of shown is "Largest so far: Dinner at 300"
```

Nothing has compiled or run this program yet; it is written by hand against the rules above. Under build step 1 (section 12) it becomes one of the compiler's tests, with fixed expected output.

## 14. Out of scope and decisions

### Out of scope for v0

- Numbers with more than four decimal places, and floating point. Data files with more places fail to load (failure 6).
- Joining, splitting, searching or measuring text
- Removing items from lists and tables
- Lists of lists, and records with list or record fields
- Counting down in `for each … from … to`
- Handling a run-time failure inside the program
- Programs spread over several files (planned for v0.1, section 16)
- Networking, databases and graphical interfaces
- Freeing memory, and any optimisation
- Calling C libraries
- Any platform beyond the one v0 target

### Decided in this revision

The open decisions from the 16 Nov draft, with the outcome:

| Decision | Outcome | Reason |
|---|---|---|
| Assignment wording | `set a to 10`; `as` kept for types and conversion | `as` already means type, in two places |
| `add` on lists and tables | **Changed:** a separate verb, `append` | A reader of `add 5 to scores` should not need the type of `scores` to know whether it sums or appends (rule 2: one form never means two ideas) |
| Feature input types | Written with `needs … as …` | Inferring them from callers would stop a feature being readable on its own, and agents would have to guess |
| Calling a feature | `with` for calls, `of` for fields and built-ins | Keeps reading and running visibly different |
| Entry point | The feature named `start` | No extra block kind needed |
| Test checks | `expect` plus any condition | One form, reusing conditions |
| Target platform | x86-64 Linux, kernel 5.6+ | Direct system calls in a static executable are only supported there (section 12) |

### Still open

| Decision | Notes |
|---|---|
| Language the compiler is written in | Not chosen. It needs good byte-buffer handling and easy distribution as one binary. |
| What the step-through viewer is built with | Not chosen (section 15) |

**Introduced in the 16 Nov draft without prior discussion:** `note`, `ask`, `needs`, `give`, `run`, `repeat while`, `for each … from … to`, `load`, `save`, `yes` and `no`, `empty list of`, and the built-ins `count`, `first`, `last`, `item` and `remainder`.

**Introduced in this revision without prior discussion:** see Appendix B.

## 15. Visual modes

Gloss has two visual modes. The flowchart is part of v0, because seeing the flow of a program is what the language is for. The step-through viewer is the first release after v0. Both are on demand: nothing is drawn unless a command asks for it.

| Mode | Release | Shows | Built from | Best for |
|---|---|---|---|---|
| Flowchart | v0 | One feature as boxes and arrows: steps, branches and loops | The program's structure, without running it | Programmers who want the shape of the logic at a glance |
| Step-through | v0.1 | The program running, one statement at a time, forwards and backwards | The trace event file | Anyone following what the values do |

### Flowchart

- One chart per feature. Statements are boxes. Each `if` is a branch labelled yes and no, and each loop is an arrow back to its condition.
- `skip` is an arrow back to its loop's condition, `stop` is an arrow to the box after its loop, and `give` is an arrow to the feature's end.
- A call to another feature is a box labelled with that feature's name; its chart is drawn separately.
- Box labels are the source lines themselves, so the chart and the code never disagree.
- On request, through `gloss flowchart`, the compiler writes each chart as an SVG file itself, with no drawing tool in between. The file is named after the source and the feature, as in `expenses.category_total.svg`, and is written beside the source.
- Gloss has no unstructured jumps. Every arrow leads either forward to a later box in an enclosing block or back to the condition of an enclosing loop. So every chart can be laid out top to bottom from the program's block structure.

**v0 limits.** The flowchart has one fixed layout, with no colours, options or interaction. It is built last in v0, after Build, Test and Trace work, so it cannot delay them.

### Step-through

- The source with the current line highlighted.
- Variables as labelled boxes whose values change at each step.
- Lists and tables as rows of cells, with a marker on the item the loop is on.
- Each condition with the values that decided it.
- Feature calls as a stack, so recursion is visible.
- **Together:** the step-through viewer also displays the flowchart and highlights the box that is running.

The step-through viewer is a separate program from the compiler and is not written in Gloss. What it is built with is not decided.

## 16. After v0: programs in several files

v0.1 lets a program be split across files, so that no single file has to hold every feature. It is built after the step-through viewer. This section is a sketch to be settled once v0 exists. Its `of file.gloss` references must then be fitted into the grammar in Appendix A.

```gloss
use "data.gloss"
use "reports.gloss"
use "billing/reports.gloss"

feature start
  load expenses of data.gloss
  run print_report of reports.gloss
  run print_invoice of billing/reports.gloss
  show "Food this month: ", monthly_total of reports.gloss with "food"
```

- **One form.** A `use` line at the top of a file names another Gloss file in the program's folder or below it.
- **A file has one spelling.** A file is always written as its path from the program's folder, with its `.gloss` ending, exactly as on the `use` line. Two files with the same name in different folders therefore never clash, and there is no renaming.
- **Everything from another file says so.** A feature, record or table defined in another file is named with `of` and the file. Examples: `run print_report of reports.gloss`, `load expenses of data.gloss`, and `Expense of models.gloss with name "Lunch", amount 120`. A name with no file always belongs to the current file, so a reader never has to look up where something comes from.
- **The ending marks a file.** Anything ending in `.gloss` is a file, so `expenses of data.gloss` cannot be confused with a field such as `amount of expense`.
- **Names need only be unique within a file.** Two files may each have a `total`, because every mention says which one it means.
- **Verbose on purpose.** Long references are accepted for the reader's sake. They are resolved at build time, so their length costs nothing when the program runs.
- **One starting point.** Only the file given to `gloss build` may contain `feature start`.
- **Permissions cover every file.** The list shown at build time, and the `.allow` file, include the tables of all used files.

**Flowcharts follow the files.** `gloss flowchart` draws a chart for every feature in the main file and in every used file. A call to a feature from another file is still one box, labelled with the feature's name and the file it lives in. Charts are never merged across calls, so a chart stays the size of its feature.

> **To consider when v0.1 is designed: a program overview chart.** Per-feature charts do not show how a multi-file program fits together. A single chart of which feature calls which, grouped by file, would. It is not decided and not designed; it is recorded here so that it is not lost.

**Left out on purpose:** choosing only some names from a file, renaming on the way in, and using files from outside the program's folder. Each adds a second way to refer to the same thing.

## Appendix A. Grammar

This grammar is the reference for the whole language. Where prose and grammar disagree, the grammar is right and the prose is a bug.

**Tokens:**

- `NAME` starts with a lowercase letter.
- `RECORD_NAME` starts with a capital letter.
- `FACT` is one of `count`, `first`, `last` and `whole`.
- `NUMBER` is digits, optionally followed by `.` and one to four digits. It has no sign.
- `TEXT` is double-quoted, with `""` inside meaning one `"`.
- `DIGIT` is a single digit from 0 to 4.
- `NL`, `INDENT` and `DEDENT` come from two-space indentation, after continuation lines (a line ending in a comma) have been joined.

**Notation:** `{ x }` means zero or more of `x`, and `[ x ]` means `x` is optional.

```
program      = { top_level } ;
top_level    = note | record | table | feature | test ;

record       = "record" RECORD_NAME NL INDENT field_decl { field_decl } DEDENT ;
field_decl   = NAME "as" plain_type NL ;
table        = "table" NAME "of" RECORD_NAME "in" TEXT NL ;
feature      = "feature" NAME NL INDENT [ needs ] statement { statement } DEDENT ;
needs        = "needs" input_decl { "," input_decl } NL ;
input_decl   = NAME "as" type ;
test         = "test" TEXT NL INDENT statement { statement } DEDENT ;

plain_type   = "number" | "text" | "truth" ;
item_type    = plain_type | RECORD_NAME ;
type         = item_type | "list" "of" item_type ;

note         = "note" WORDS NL                      (* the rest of the line is ignored *)
             | "note" NL INDENT ANY_LINES DEDENT ;  (* every line under it is ignored *)

block        = NL INDENT statement { statement } DEDENT ;
statement    = note
             | "set" target "to" expr NL
             | "add" arith "to" target NL
             | "subtract" arith "from" target NL
             | "multiply" target "by" arith NL
             | "divide" target "by" arith NL
             | "append" value "to" NAME NL
             | "show" arith { "," arith } NL
             | "ask" arith "into" NAME NL
             | "if" expr block { "otherwise" "if" expr block } [ "otherwise" block ]
             | "for" "each" NAME "in" arith block
             | "for" "each" NAME "from" arith "to" arith block
             | "repeat" "while" expr block
             | "skip" NL
             | "stop" NL
             | "give" expr NL
             | "run" NAME [ "with" arith { "," arith } ] NL
             | "load" NAME NL
             | "save" NAME NL
             | "clear" NAME NL
             | "expect" expr NL
             | "input" arith { "," arith } NL ;

target       = NAME
             | NAME "of" target
             | "item" position "of" target ;

expr         = negation { "and" negation }
             | negation { "or" negation } ;         (* and/or never mix unparenthesised *)
negation     = [ "not" ] comparison ;
comparison   = value [ compare_op value | "is" [ "not" ] "number" ] ;
compare_op   = "is" [ "not" ]
             | "is" "greater" "than" | "is" "less" "than"
             | "is" "at" "least"     | "is" "at" "most" ;

value        = open_form | arith ;
open_form    = NAME "with" arith { "," arith }                     (* call a feature *)
             | RECORD_NAME "with" NAME arith { "," NAME arith }   (* build a record *)
             | "list" "of" arith { "," arith } ;                   (* build a list *)

arith        = product { ( "+" | "-" ) product } ;
product      = converted { ( "*" | "/" ) converted } ;
converted    = signed [ "as" ( "number" | "text" [ "with" DIGIT "places" ] ) ] ;
signed       = [ "-" ] fact ;
fact         = NAME "of" fact                      (* field read *)
             | FACT "of" signed                    (* built-in fact *)
             | "item" position "of" fact
             | "remainder" "of" signed "by" signed
             | primary ;
position     = NUMBER | NAME | "(" expr ")" ;
primary      = NUMBER | TEXT | "yes" | "no" | "shown" | NAME
             | "empty" "list" "of" item_type
             | "(" expr ")" ;
```

**Rules the grammar cannot express:**

- A `whole` or `remainder` fact directly followed by `+ - * /` is rejected (section 6).
- A loop variable cannot be set or changed with `add`, `subtract`, `multiply` or `divide`; only its fields can (section 4).
- A bare `NAME` in an expression is a variable or a feature with no inputs. They cannot share a name (section 3).
- `expect`, `input` and `shown` appear only inside tests.
- `skip` and `stop` appear only inside loops.
- A `set` whose right side is the target combined with one other value is rejected (section 7).
